# Design

## Context

См. `proposal.md` — Why. Здесь только то, на что опирается реализация.

- Цикл (`lib/loop.js`) уже умеет распознавать группы по `N.M` (`lib/groups.js`) и открывать сессию на границе (`openSession` в `lib/session.js`), но точка решения — `targetFor()`, то есть переход к следующей задаче. Финальная группа при этом ничем не отличается от «просто конца списка».
- Сессия создаётся через `sessionController.create()` и получает turn через `sessionController.prompt()`; `whenIdle()` раннера ждёт покоя агента. Этот путь уже headless: первая задача новой группы уходит именно так.
- `ctx.subprocess.spawn()` принимает argv-массив, явные stdio-режимы и `graceMs` — этим уже пользуется `lib/openspec.js`.
- Settings показывает плагину только **volatile**-поля Config: `describe()` пропускает запись, если `volatileForm(schema)` пуст. Сейчас volatile-полей нет, поэтому страницы настроек у плагина нет вовсе.
- Запись настроек идёт `configForms.get(entryId).mutate(...)` → `remote.settings` → `ConfigEditor` → профильный `cordis.patch.yml`, с revision-фенсингом и применением через `loader/volatile-update`.
- Клиентская половина подключается декларацией `dsh.client` и файлом `exports["./client"]` в формате `window.__ModuleLoader__.load({ id, factory: (require) => … })`; сборщик не обязателен — этот формат воспроизводится одним файлом.
- Прецедент персистентности настроек мимо репозитория: `dsh-ssh-ops` хранит `~/.dsh/storages/ssh_ops_settings.json`.

## Goals / Non-Goals

**Goals:**

- Настройки плагина редактируются в Settings dsh и применяются без перезапуска Harness.
- Каждая группа задач (включая финальную) заканчивается ревью и коммитом без участия пользователя.
- Сообщение коммита задаётся один раз за прогон и переживает прерывание.
- Инструмент коммита — часть конфигурации, а не кода.

**Non-Goals:**

- Разбор ответа модели и любые решения «по вердикту» ревьюера: ревью и исправление — один turn.
- Коммит после каждой задачи или по расписанию.
- Изменение правил выбора задач, сжатия и переноса сессии на границе.
- Синхронизация состояния между процессами и восстановление прогона после рестарта (остаётся D8).
- UI для просмотра или правки сохранённого сообщения коммита.

## Decisions

### D12. Настройки — volatile-поля Config плюс своя страница `settings.section`

На странице шесть настроек:

- коммиты: `commit.enabled` (переключатель), `commit.tool` (Git / GitButler);
- ревью: `review.enabled` (переключатель);
- сжатие: `compaction.midTask` (переключатель), `compaction.onFailure` (Break / Continue);
- протокол: `protocol.systemSection` (переключатель).

Первые три — новые поля; последние три существуют и переводятся в `.volatile()`. Без volatile поле не попадает ни в одну форму, а запись через `configForms` отклоняется (`isVolatilePath`). Обычными остаются `change`, `compaction.retry.*` и `openspec.timeoutMs`: это настройка профиля, меняется редко, а retry-параметры имеют смысл только вместе с политикой.

Дефолты новых полей — дополнение к контракту D11 (архивный design.md прошлого change), поэтому блок помечен `<!-- config-defaults -->`: `test/config.test.mjs` собирает такие блоки по всем `design.md` и сравнивает их объединение с `Config({})`, так что каждое решение описывает только свои ключи, а не повторяет D11.

<!-- config-defaults -->
```json
{
  "commit": {
    "enabled": true,
    "tool": "git"
  },
  "review": {
    "enabled": true
  }
}
```

`commit.tool` принимает только `git` и `gitbutler`; неизвестный инструмент отклоняется при разборе конфигурации так же, как неизвестный `onFailure`. Включённые по умолчанию коммит и ревью означают, что после обновления каждая группа сразу заканчивается ревью и коммитом — это и есть целевое поведение change.

Следствия перевода существующих полей в volatile:

- в разрешённом `Config` они становятся `Volatile`-обёртками, и всё, что их читает, обязано вызывать `.get()`: `onFailure` — при старте прогона (loop), `midTask` и `systemSection` — при сборке гейта и секции на этот прогон (`lib/control.js`).
- `resolveConfig` не должен повторно валидировать уже разрешённый конфиг с обёртками; для прямого монтирования (тесты) он по-прежнему заполняет дефолты.
- значения по умолчанию и семантика не меняются; сохранённые в профиле обычные значения остаются валидными.
- прогон берёт снимок значений на старте, поэтому переключение в середине применяется следующим прогоном. Исключение — `commit.tool`: он читается в момент коммита, чтобы инструмент можно было сменить, не перезапуская прогон.

Страница — запись в `settings.section` с id `openspec-taskloop`, label «OpenSpec Taskloop», order после Models. Запись сразу, без кнопки Save, как у темы и языка. Подсказка у `protocol.systemSection` говорит, что её включают вместе с `compaction.midTask`. Плагин вызывает `ctx.settings.configure({ auto: false })`, чтобы не появлялась вторая, автоматическая страница того же namespace в Settings → Plugins.

Альтернативы:
- *Только автоматическая страница в Settings → Plugins.* Дешевле (ноль клиентского кода), но пользователь просил вкладку рядом с General и Models, а авто-страница ещё и не покажет enum как выбор.
- *Обычные (не volatile) поля.* В Settings не отображаются вовсе и меняются только правкой профиля.

### D13. «Группа завершена» — событие цикла, а не переход

Проверка ставится в `lib/loop.js` сразу после подтверждения, что отправленная задача отмечена: для grouped-прогона считается, что все задачи её группы в последнем чтении `tasks.md` отмечены. Это срабатывает и для последней группы (иначе `all_done` остался бы без ревью), и при возобновлении прогона, который остановился уже после последней задачи группы.

Порядок на границе: верификация задачи → `onGroupComplete` (ревью + коммит) → выбор следующей задачи → `targetFor()` открывает сессию следующей группы. То есть ревью-сессия и рабочая сессия следующей группы — разные сессии, как и требовалось.

Flat-прогон (нет `N.M`) групп не имеет: `onGroupComplete` вызывается один раз, когда следующей задачи нет.

Альтернатива — вешать ревью на `TRANSITION.newGroup` — отклонена: последняя группа не имеет перехода, и её результат остался бы без проверки и коммита.

### D14. Ревью — одна инструкция в новой сессии, approval `never`

Инструкция собирается как обычное user-сообщение (`lib/message.js`) и отправляется через `sessionController.prompt`; ждём `whenIdle()`. Промпт называет change и диапазон задач группы, требует автономности (без вопросов), разрешает исправлять только однозначные значимые дефекты и при чистоте — перечислить проверенное.

На время ревью агенту ставится approval-политика `never`: unattended-turn не должен зависнуть на запросе подтверждения, на который некому ответить. Правки внутри workspace проходят без approval; всё, что требует эскалации, детерминированно отклоняется.

Альтернативы:
- *Два turn с вердиктом.* Требует машиночитаемого ответа модели и чтения лога сессии — хрупко (обсуждалось, отклонено пользователем).
- *Не менять approval.* Turn может встать на подтверждении навсегда, а прогон — ждать его.

### D15. Коммит — прямой вызов инструмента, без модели

Коммит выполняет плагин через `ctx.subprocess.spawn` с argv-массивом (никакого shell):

- `git`: `git add -A` затем `git commit -m <msg>`;
- `gitbutler`: `but commit -m <msg>`.

Сообщение передаётся одним argv-элементом, поэтому кавычки и переводы строк не требуют экранирования. Код возврата — данные, как у `openspec`: ненулевой код превращается в остановку прогона с отчётом (инструмент, код, хвост stderr), потому что задача уже выполнена и молча продолжать нельзя.

Перед коммитом проверяется `git status --porcelain`: пусто — коммит пропускается с пометкой в отчёте (например, пользователь закоммитил сам).

Альтернативы:
- *Отдельный скрипт в пакете.* Дублирует то, что плагин и так делает одним вызовом, и добавляет вторую точку отказа.
- *Поручить коммит модели.* Нарушает требование «без участия модели» и делает результат недетерминированным.

### D16. Сообщение коммита — файл в `~/.dsh/storages`

Файл `~/.dsh/storages/openspec-taskloop.json` (путь через `profileContext.home`), структура `{ changes: { "<cwd>#<change>": { message, updatedAt } } }`. Запись атомарная (временный файл + rename).

- Спрашивается в `startTaskStep` до первого turn, если для ключа нет записи.
- Отмена вопроса — отказ в запуске: ничего не отправлено, файлы не изменены.
- При `all_done` запись удаляется; при любом другом конце — остаётся.
- В репозиторий не пишем: автокоммит `git add -A` затащил бы служебный файл в коммит.

Альтернатива — `ctx.storageDomain` (как в `dsh-ssh-ops`): каноничнее, но требует zod-схем и версионирования домена ради одной строки; файл проще и уже имеет прецедент.

### D17. Коды завершения и отчёт

Пайплайн возвращает отдельный исход (`review` / `commit`), который `lib/loop.js` превращает в `LoopOutcome`; `lib/control.js` рендерит его в текст команды. В отчёт попадают: id ревью-сессий, хэши коммитов (или «нечего коммитить»), ошибка инструмента. Отчёт по-прежнему уходит в исходную сессию — она единственная, за которой следит пользователь.

## Risks / Trade-offs

- **Turn ревьюера повиснет на approval или вопросе** → approval `never` + прямой запрет вопросов в промпте; turn, который всё-таки спросил, завершится отказом инструмента, а не остановит прогон.
- **`git add -A` захватит чужие незакоммиченные правки** → принятое поведение («коммитим всё, что не закоммичено»); фиксируется в README и в отчёте коммита. Альтернатива — снимок дерева на старте прогона — отвергнута как заметно более сложная.
- **`but commit` зависит от состояния GitButler (ветка, assignments)** → ошибка инструмента показывается целиком, прогон останавливается; повторный `/taskloop` продолжит с того же места, задача не потеряна.
- **Rевью-сессия остаётся в сайдбаре** → это след ревью; её id и хэш коммита есть в отчёте, при необходимости её можно переименовать вручную.
- **Volatile-поля и `resolveConfig()`** → `apply` получает уже разрешённый конфиг с `Volatile`-обёртками; повторная валидация должна сохранять обёртки, а не пытаться сериализовать их. Проверяется первым тестом конфига.
- **Перевод существующих полей в volatile меняет их тип** → все чтения `midTask`, `systemSection` и `onFailure` переводятся на `.get()`; тест конфига фиксирует, что дефолты не изменились, а обычные значения из профиля по-прежнему принимаются.
- **Переключение настроек в середине прогона** → прогон использует снимок со старта; на экране это не отличается от «применится к следующему прогону», и подсказка у переключателей об этом не умалчивает.
- **Правка настроек во время активного прогона** → новые значения читаются следующим шагом, а не пересобирают текущий; для `commit.tool`, который берётся в момент коммита, это ровно то, что нужно.
- **Файл сообщения привязан к пути проекта** → перенос каталога теряет сохранённый текст; пользователь введёт его заново, ничего не ломается.
- **Ошибка коммита останавливает прогон** → выбранная задача уже отмечена; повторный запуск продолжит со следующей, коммит можно выполнить вручную.

## Migration Plan

1. Опубликовать версию с новым `Config` и клиентской половиной; существующие профили получают значения по умолчанию (`commit.enabled: true`, `tool: git`, `review.enabled: true`), а переведённые в volatile поля сохраняют свои значения и дефолты (`midTask: false`, `systemSection: false`, `onFailure: break`).
2. При первом `/taskloop` после обновления появляется вопрос о сообщении — это и есть миграция пользовательского сценария.
3. Откат: удалить пакет/строку из профиля; файл сообщения в `~/.dsh/storages` остаётся и безвреден. Формат сессий и `tasks.md` не меняется.
