# Design

## Context

Коммит группы сегодня — две команды без промежуточного чтения: `git status --porcelain` решает, есть ли что коммитить, дальше `git add -A` и `git commit -m`, либо `but commit [-b <ветка>] -m` (`lib/commit.js`, задачи 4.1–4.3 базового change). Порядок неизменен во всех прошлых change: ворота — дешёвое чтение, инструмент — исполнение. Оба инструмента читают одно и то же дерево.

`commit.tool` — volatile и читается в момент коммита (`lib/control.js`), поэтому переключение инструмента посреди прогона законно, а ворота стоят до этого чтения. `tasks.md` лежит под `openspec/changes/<change>/`, то есть галочки, которые ставит сам прогон, попадают в тот же коммит, что и код группы.

Установленный `but` 0.22.3 не имеет флага исключения: справка `but commit` описывает только позиционные `CHANGES` («a file or a hunk»), `--empty`, `-i`, `-b`, `-A`, `-B`. У `git` исключение есть — pathspec magic `:(exclude)`.

## Goals / Non-Goals

**Goals:**

- Одно множество изменений для ворот и для коммита при любом инструменте: что посчитали коммитируемым, то и коммитим.
- `git` и `but` ведут себя одинаково при выключенной настройке, включая случай «изменился только `openspec/`».
- Ни одного нового вида исхода коммита: выключенная настройка не создаёт нового сбоя, только другое множество изменений.

**Non-Goals:**

- Не вводится список исключаемых путей в конфигурации: исключение одно и фиксировано — `openspec/` в корне проекта.
- Не трогается `git add -A` для включённой настройки: поведение по умолчанию остаётся побайтово прежним.
- Не решается вопрос «куда девать накопленные незакоммиченные изменения `openspec/`» — их коммитит пользователь, README об этом предупреждает.

## Decisions

### D1. Настройка `commit.openspec` — volatile, по умолчанию `true`

Поле рядом с `commit.enabled` и `commit.tool`, читается в момент каждого коммита, как инструмент (D12 базового change). Причина та же: переключение посреди прогона должно применяться к следующей группе, а не к следующему запуску. Значение по умолчанию `true` — существующие профили не меняют поведения, и «выключить» остаётся осознанным действием.

Альтернативы: сделать поле обычным (профильным) — тогда страница настроек не может им управлять, а это ровно то место, где пользователь его ищет; назвать `commit.includeOpenspec` — отвергнуто, `commit.openspec` читается как «коммитить openspec» и совпадает с подписью строки.

### D2. Одно чтение `git status --porcelain=v1 -z -uall`, фильтрация в JS

Ворота перестают быть проверкой «stdout не пуст» и становятся разбором списка путей: `-z` (NUL-разделители) убирает кавычки вокруг путей с пробелами и не-ASCII, `-uall` разворачивает untracked-каталоги в файлы — иначе `?? dir/` уйдёт в `but` каталогом, а он принимает файлы.

Фильтр («первый сегмент пути равен `openspec`») живёт в JS, а не в pathspec, потому что ворота стоят **до** чтения `commit.tool`: pathspec-версия ворот и `but`-версия исполнения разошлись бы при переключении инструмента посреди прогона и дали бы «есть что коммитить» → «нечего коммитить» уже внутри инструмента.

Альтернативы: `git status --porcelain -- . ':(exclude)openspec'` для `git` и полный список для `but` — два разных ответа на один вопрос; `porcelain=v2` — больше полей, но те же пути, и разбор `-z` v1 уже нужен для `but`.

### D3. `git`: pathspec-исключение в `add` **и** в `commit`

`git add -A -- . ':(exclude)openspec'` не индексирует `openspec/`, но `git commit -m` коммитит индекс целиком — то есть предварительно застейдженный пользователем openspec-файл всё равно уехал бы в коммит. Поэтому при выключенной настройке коммит идёт с тем же pathspec: `git commit -m <msg> -- . ':(exclude)openspec'`. Дерево перечисленных путей и так полностью проиндексировано предыдущей командой, так что содержимое коммита не меняется; меняется только то, что индекс ограничен.

Индекс пользователя плагин при этом не переписывает: `git reset -- openspec` отбросил бы чужую индексацию, а это не его решение.

Альтернатива — `git add -A`, затем `git restore --staged openspec` — отвергнута: стирает подготовленные пользователем изменения и делает плагин владельцем индекса.

### D4. `but`: позиционные `CHANGES` из того же списка, с порогом на длину argv

`but commit` не умеет исключать, поэтому при выключенной настройке список файлов вне `openspec/` передаётся аргументами: `but commit [-b <ветка>] -m <msg> <файл>…`. Источник — тот же разбор из D2: отдельного чтения `but status` не добавляется.

Список может оказаться длинным: предел командной строки в Windows — около 32 тысяч символов, и группа, тронувшая сотни файлов, упрётся в него уже после сделанной работы. Поэтому при списке сверх бюджета (200 путей) коммит идёт без `CHANGES`, а доклад говорит, что изменения `openspec/` в этот коммит попали. Деградация видимая и редкая, в отличие от падения argv.

Альтернативы: CLI-идентификаторы изменений из `but status --json` — точнее по хункам, но разбор этого документа в базовом change уже признан терпимым и недокументированным, а второй потребитель того же JSON дороже файлового списка; отказ от `but` в этой настройке — отвергнут пользователем.

### D5. Исход `empty` не меняется, меняется фраза; в докладе видно, что осталось за бортом

Новый вид исхода не вводится: «изменился только `openspec/`» — это то же «коммитить нечего», и прогон обязан продолжиться так же (переход к следующей группе, пауза, что угодно). Отличается только предложение доклада: «вне `openspec/`». Для состоявшегося коммита исход получает число исключённых изменений, и доклад добавляет предложение о том, что они остались незакоммиченными, — иначе выключенная настройка молча копит грязь в дереве.

### D6. Страница: новая строка второй, `Protocol section` — сразу после `Compact inside a task`

`Commit openspec files` стоит сразу под `Commit after each task group`: это уточнение того же решения, и читать его надо раньше выбора инструмента. `Protocol section` переезжает из конца списка вплотную к `Compact inside a task` — README связывает их как пару, которую включают вместе, и разрыв между ними в десять строк эту связь прятал.

Альтернатива — оставить `Protocol section` последней строкой — отвергнута пользователем; вариант «сразу после `onFailure`» он тоже отклонил, потому что он разрезает блок ретраев.

### D7. Дефолт документируется блоком `config-defaults`

`test/config.test.mjs` сливает блоки всех changes поверх базового контракта D11, поэтому здесь фиксируется только новый ключ.

<!-- config-defaults -->
```json
{
  "commit": {
    "openspec": true
  }
}
```

## Risks / Trade-offs

- **`but commit <файлы>` на живом проекте не проверен**: справка обещает приём файла, но поведение с путями, которые GitButler ещё не назначил, не описано. → Проверка отдельной задачей на живом проекте до релиза; при отказе инструмента прогон останавливается существующим правилом сбоя коммита, ничего не теряя, а группа уже отмечена в `tasks.md`.
- **Длинный список аргументов для `but`** упирается в предел ОС. → Бюджет 200 путей и видимая деградация из D4.
- **Незакоммиченные изменения `openspec/` копятся весь прогон** и достаются пользователю в наследство. → Доклад называет число исключённых изменений, README предупреждает; это и есть цель настройки, а не побочный эффект.
- **Пути с не-ASCII и пробелами**: `-z` их сохраняет, но `but` получает их как отдельные argv-элементы. → Уже действующее правило «каждый аргумент — один argv-элемент», проверяется тестом с путём, содержащим пробел.
- **Разбор porcelain — новый код на пути, который раньше был одной проверкой**. Ошибка разбора превращается в неверное «нечего коммитить». → Отдельная чистая функция с тестами на `R`/`C`-записи, `??`, пустой вывод и вывод без завершающего NUL.
