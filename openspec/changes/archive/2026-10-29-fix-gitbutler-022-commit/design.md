# Design

## Context

Плагин коммитит через GitButler командой `but commit`, а новую ветку создаёт через `but branch new`. Эти команды строятся в `lib/commit.js` (`buildCommitCommands`). Установленный GitButler CLI 0.22.3 изменил синтаксис обеих: `but commit` требует флаг `-b` для ветки, а `but branch new` использует `-A`/`--above` для стекования (флаг `-a`/`--anchor` исчез). См. proposal.md — Why. Плагин до сих пор строит старую форму, поэтому коммит на 0.22.x падает (`Could not find uncommitted change: '<branch>'`), останавливая прогон на границе группы.

## Goals / Non-Goals

**Goals:**
- Перевести `but commit` и `but branch new` на синтаксис GitButler ≥ 0.22.0.
- Добавить fail-closed проверку минимальной версии GitButler, чтобы поддерживать **один** набор команд и не ветвить argv по версии.
- Актуализировать юнит-тесты под новые argv и под проверку версии.

**Non-Goals:**
- Не поддерживать синтаксис GitButler < 0.22.0 (старое поведение не сохраняется).
- Не чинить состояние `setup_required` (`but status` возвращает «unable to open database file» в неинициализированном проекте) — это отдельная проблема окружения, не связанная с синтаксисом команд.
- Не менять путь коммита через `git`.

## Decisions

### D1. Версия GitButler проверяется fail-closed, как версия openspec

Зеркалим существующую проверку `openspec --version` (задача 9.1 / дизайн D20 в `lib/openspec.js`): плагин читает `but --version` один раз за прогон, парсит первое `X.Y.Z` из ответа (установленный CLI печатает `but 0.22.3`), сравнивает с минимумом `0.22.0` численно по компонентам и при версии ниже или нераспознанном ответе останавливает прогон с советом обновить GitButler. Это тот же fail-closed принцип: нераспознанная версия означает неподтверждённый контракт, и молча продолжать хуже, чем сказать об этом.

Альтернатива — поддерживать оба синтаксиса с выбором по версии — отклонена: и `but commit -b`, и `but branch new -A` доступны только с 0.22.x, так что дуальный путь не несёт пользы, а добавляет два набора argv, два набора тестов и два способа сломаться. Один гейт даёт один контракт.

### D2. Гейт живёт в карточке ввода GitButler, а не на старте прогона

Проверка версии выполняется только когда `commit.tool` равен `gitbutler`, там же, где читаются applied-ветки и спрашивается ветка — в `resolveCommitInput` (`lib/control.js`, строка ~420, задача 7.3): `git`-прогон не трогает `but` вообще, поэтому спрашивать ещё и его версию без надобности не стоит. `but status --json` и так происходит до вопроса о ветке; версия читается перед ним, тем же вызовом subprocess.

Это отличается от гейта openspec, который стоит самым первым для любого прогона — потому что `openspec` нужен всем прогонам, а `but` — только GitButler. Место проверки — `lib/environment.js`/`lib/control.js`, в той же карточке, что и вопрос о ветке.

### D3. Новый синтаксис обеих команд

`lib/commit.js buildCommitCommands` строит:
- `but commit` → `['commit', '-b', <branch>, '-m', <message>]` (было `['commit', <branch>, '-m', <message>]`); без ветки остаётся `['commit', '-m', <message>]`.
- `but branch new` → `['branch', 'new', <name>, '-A', <anchor>]` (было `-a <anchor>`).

Аргументы остаются отдельными элементами argv — сообщение не экранируется, как сейчас (дизайн D15).

### D4. Минимум `0.22.0` — константа

`MIN_GITBUTLER_VERSION = '0.22.0'` в модуле проверки версии (аналог `MIN_OPENSPEC_VERSION`). Порог взят из факта, что оба новых синтаксиса (`-b`, `-A`) появились в 0.22.x, описанного в `but commit --help` и `but branch new --help` установленной 0.22.3.

### D5. Тесты

- `test/commit.test.mjs`: обновить точные argv для `but commit -b <branch>` и `but branch new <name> -A <anchor>`; добавить ветку «без аргумента `-b`, когда ветки нет» (= «без канала вопросов», уже есть как `but commit -m`).
- Новый модуль проверки версии: тесты на парсер `X.Y.Z`, сравнение `0.21.0 < 0.22.0`, `0.22.0` = минимум, `1.x > минимум`, пре-релиз и мусор в выводе — по образцу тестов версии openspec.

## Risks / Trade-offs

- **Проверка версии падает на сломанном `but`** → гейт останавливается fail-closed; текст ошибки несёт вывод инструмента и подсказку о настройке, как в задаче 7.3.
- **`but branch new` настоящего CLI может отличаться от справки** → точная форма `-A <anchor>` закреплена по `but branch new --help` установленной версии; если реальный вывод вернёт другую форму, тест на живой CLI это покажет.
- **`setup_required` блокирует реальный коммит, но не версию** → `but --version` работает без настроенного проекта (проверено), так что гейт не столкнётся с проблемой БД; сам `setup_required` в этот change не входит (Non-Goals).
- **Предыдущий change `add-taskloop-review-commit` ещё не заархивирован** → требования, которые этот change MODIFY, пока лежат в delta предыдущего, а не в главной спеке; validate предупреждает «Archive would refuse … not found». Это ожидаемо при последовательной архивации: сначала архивируется `add-taskloop-review-commit`, затем этот change, и MODIFIED резолвится. Пока оба open, `openspec validate` всё равно считает change валидным.

## Migration Plan

1. Обновить `lib/commit.js` (D3) — оба argv.
2. Добавить проверку версии (D1–D2, D4) и встроить в `resolveCommitInput`.
3. Актуализировать тесты (D5).
4. Обновить README и подсказку «Commit tool» на новый синтаксис и минимум 0.22.0.
5. Ручная проверка на живом GitButler: `but --version` соответствует 0.22.3, затем коммит в существующую ветку через `but commit -b <branch>`.

Откат: вернуть прежние argv и убрать гейт — изменение локализовано в `lib/commit.js` и карточке ввода; тесты откатываются вместе с кодом.
