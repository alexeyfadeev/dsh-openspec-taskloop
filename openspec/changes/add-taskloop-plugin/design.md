# Design

## Context

Плагин живёт внутри Cordis-композиции Harness и не имеет собственного UI: всё видимое — это сообщения в сессии и текст результата команды. Доступные Host-сервисы: `commands`, `agents`, `sessionController`, `compaction`, `subprocess`, `systemPrompt`, `userQuestions`, `workspaceRegistry`, `tokenMeter`.

Опорные факты, на которых держится дизайн:

- `openspec instructions apply --json` отдаёт `tasks[] = { id, description, done, sourcePath, line }`, `progress` и `state` (`ready` / `blocked` / `all_done`). Сквозной `id` — порядковый; номер `N.M` существует только в тексте `description`.
- `agent.followup()` ставит turn и будит драйвер; `agent.whenIdle()` резолвится, когда вся активность агента сошлась в покой, включая чужие сообщения, пришедшие в это время.
- `compaction.compactNow()` требует idle-агента и бросает `ManualCompactionError` с закрытым набором кодов; `compactIfNeeded(agent, 'pressure', signal)` безопасен на границе шага и сам решает по порогу.
- В профиле стоит `compaction-basic: auto: false`, то есть автоматического сжатия нет и вся ответственность за контекст лежит на этом плагине.
- Соседние по каталогу плагины (`dsh-opencode-session`, `dsh-llm-acp`) показывают принятую форму поставки: отдельный пакет, `link:` в профиле, `insert:` в `cordis.patch.yml`.

## Goals / Non-Goals

**Goals:**

- Один детерминированный дирижёр: ровно одна задача за turn, решение о следующем шаге принимает код, а не модель.
- Восстановление позиции прогона из `tasks.md`, а не из памяти плагина.
- Предсказуемое сжатие контекста на переходах и явная политика на его отказ.
- Переход между группами задач со сменой сессии, не теряя change и протокол.

**Non-Goals:**

- Клиентская половина и любые UI-индикаторы прогона.
- Персистентность состояния прогона между перезапусками процесса.
- Проверка качества выполнения задачи (тесты, ревью) — плагин не верифицирует работу, только читает галочку.
- Параллельные прогоны, несколько change одновременно, автоархивация change.
- Правка `tasks.md` плагином.

## Decisions

### D1. Цикл — асинхронная цепочка ожиданий, а не набор подписок на события

Шаг: `followup()` → `await agent.whenIdle()` → перечитать состояние → решить. Альтернатива — слушать `session/event` с `turn/end` и держать машину состояний на событиях — отклонена: `turn/end` приходит и на пользовательские turn, а порядок «наше сообщение / чужое сообщение / компакция» пришлось бы восстанавливать вручную. Цепочка ожиданий даёт ту же детерминированность без теневого состояния.

Следствие: если пользователь пишет в сессию во время шага, `whenIdle` дождётся и его turn. Это не ломает прогон — после покоя плагин просто перечитает `tasks.md`, — но означает, что вопросы пользователя обрабатываются между задачами, а не внутри них.

### D2. Инструкция задачи едет в сообщении, а не в системном промпте

Текст сообщения: `Используя навык <путь> выполни task N.M, далее - пауза.` плюс вторая строка-адрес с именем change и строкой файла. Причины: такая формулировка проверена на практике; номер задачи не попадает в системный промпт, поэтому префикс не меняется и prompt-кэш не инвалидируется на каждом шаге; сообщение видно в логе сессии, что делает поведение дирижёра отлаживаемым.

Альтернатива — держать номер задачи в системной секции — отклонена: секция собирается на каждый запрос, и её изменение между задачами обнуляет кэш префикса.

### D3. Статичная секция протокола — опциональна и по умолчанию выключена

Секция нужна ровно в одном случае: когда включено сжатие внутри задачи и сводка может вытеснить сообщение с «далее — пауза». Секция содержит только инвариант («одна задача за turn»), без номера задачи, поэтому остаётся статичной и кэш не ломает. Она регистрируется на `agent.ctx` в начале прогона и снимается при его завершении.

### D4. Завершение задачи читается из `tasks.md` и только оттуда

Модель ставит `[x]` сама; плагин никогда не пишет в файл задач. После `idle` он заново выполняет `openspec instructions apply --json` и ищет задачу по `sourcePath` + `line` + тексту. Отсутствие галочки — это стоп-условие, а не повод для ретрая: прогон, который сам доотмечает задачи, перестаёт быть проверяемым.

### D5. Группировка по текстовой нумерации

Номер группы извлекается из `description` регулярным выражением `^(\d+)\.(\d+)`. Если хотя бы у одной задачи префикса нет, прогон считается плоским: сессии не делятся, сжатие всё равно выполняется на каждом переходе. Альтернатива — восстанавливать группы по заголовкам `tasks.md` — отклонена: CLI не отдаёт заголовки, и группировка перестала бы совпадать с тем, что видит модель.

### D6. Новая сессия создаётся через `sessionController`, а не через `agents.create`

`sessionController.create({ workspaceId | cwd, agentPreset })` создаёт сессию и, что важно, привязывает её к workspace — иначе она не появится в сайдбаре. Дальше `sessionController.prompt(...)` ставит задачу уже в новую сессию. `ctx.agents.create` в одиночку оставил бы сессию без workspace; повторять привязку руками через `workspaceRegistry.attachSession` — дублировать логику контроллера.

Preset наследуется от исходной сессии, когда он известен, иначе берётся дефолтный.

### D7. Компакция: типизированные ретраи, порог не наш

На переходе внутри группы вызывается `compactNow`. Ретраятся только `summary`, `persistence`, `busy` — они транзиентны; `changed`, `commit`, `cancelled` терминальны, и повтор `commit` рискует применить наполовину применённую мутацию. Задержка растёт как `delayMs * factor^n` с потолком. После исчерпания попыток применяется `onFailure`: `continue` (предупреждение в доклад) или `break` (остановка прогона).

Сжатие внутри задачи — отдельный, выключенный по умолчанию механизм: `agent/pre-step` только для управляемых агентов вызывает `compactIfNeeded(agent, 'pressure', signal)`. Порог живёт в конфигурации `compaction-basic`; плагин не заводит второе число, чтобы два порога не расходились. Сбой здесь не рвёт прогон — это оппортунистическая оптимизация.

Сервис сжатия резолвится в два шага: сначала `ctx.get('compaction')` (профиль монтирует `compaction-basic` на host-плоскости), затем `agentPresets.serviceFor(agent, 'compaction')`. Второй шаг обязателен для preset-isolated профилей — shipped-профиль `@deepseek-ai/dsh-web-app` отключает host-строку и монтирует приватный `compaction-basic` внутри группы каждого пресета, поэтому host-плоскостной `get` отвечает `undefined`, хотя у агента сервис есть. Резолв идёт после того, как известен агент: реестр пресетов разрешает сервис по агенту.

### D8. Состояние прогона — в памяти, вход идемпотентен

`Map<sessionId, RunState>` живёт в процессе; после рестарта прогон просто не продолжается. `/taskloop` каждый раз заново выводит позицию из `tasks.md`, поэтому повторный вход всегда безопасен. Это осознанный размен: персистентность состояния потребовала бы домена в session log и правил восстановления, а файл задач и так является источником истины.

### D9. Бутстрап ведёт плагин, диалог с моделью начинается после него

`/taskloop` без change: `openspec list --json` → при `root: null` структурированный вопрос об инициализации → `openspec init --tools dsh` → вопрос об описании задачи → один `followup` с просьбой работать в режиме explore по навыку. Модель ведёт диалог дальше сама, а плагин в него не вмешивается: петля на этом этапе не запускается.

Альтернатива — поручить вопрос модели и ждать, пока она инициализирует проект, — отклонена: плагин не наблюдает ответ пользователя и не может определить момент, когда можно начинать цикл.

### D10. Поставка — host-only плагин без клиентской половины

ESM-пакет с `lib/index.js`, манифест `dsh.bundle.patch` указывает на `cordis.patch.yml`, установка — `link:` в профиле плюс `insert:`-запись. Клиентская половина не нужна: команда и сообщения уже отображаются существующим UI.

### D11. Контракт конфигурации и значения по умолчанию

Схема описана schemastery (`z.object`) и экспортируется как `Config`; загрузчик применяет её до `apply`, поэтому плагин получает уже разрешённый объект, где каждое значение по умолчанию заполнено.

Блок ниже — источник истины для значений по умолчанию: тест `test/config.test.mjs` разбирает его и сравнивает с результатом `Config({})`, поэтому расхождение кода и этой записи роняет тест.

```json
{
  "change": "",
  "compaction": {
    "retry": {
      "attempts": 3,
      "delayMs": 1000,
      "factor": 2,
      "maxDelayMs": 10000,
      "codes": ["summary", "persistence", "busy"]
    },
    "onFailure": "break",
    "midTask": false
  },
  "protocol": {
    "systemSection": false
  },
  "openspec": {
    "timeoutMs": 120000
  }
}
```

Семантика, которую схема не выражает:

- `change` — пустая строка означает «не указан»: выбирается change с самым поздним `lastModified`.
- `compaction.retry.attempts` — общее число вызовов `compactNow` на одном переходе, первый включён; задержка перед первым повтором равна `delayMs`, каждый следующий повтор умножает её на `factor`, но не выше `maxDelayMs`.
- `compaction.retry.codes` — только транзиентные коды; `changed`, `commit` и `cancelled` не повторяются ни при какой конфигурации (D7).
- `compaction.onFailure: break` — политика по умолчанию останавливает прогон: продолжать без сжатия значит накапливать контекст без ограничения, тогда как остановка видна пользователю в докладе (D7).
- `compaction.midTask` и `protocol.systemSection` выключены по умолчанию (D3); включать их следует вместе, потому что секция существует ровно для того, чтобы пережить сводку внутри задачи.
- `openspec.timeoutMs` — таймаут одного вызова CLI; 120 000 мс совпадает с прочими длительными ожиданиями Harness, а сам `openspec` на нормальном проекте отвечает за секунды.

### D12. Время жизни прогона принадлежит плагину, а не запросу команды

Сигнал, который команда получает в `invocation.signal`, принадлежит UI-запросу: хост обрывает его, когда закрывается соединение ответа — перезагружена вкладка, закрыто окно, пропало соединение. Прогон — это десятки turn'ов и десятки минут; запрос — нет. Поэтому слот прогона создаёт собственный `AbortController`, и единственный внешний способ остановить прогон — `/taskloop stop`; сессия, открытая на границе группы, тоже получает сигнал прогона, иначе перезагрузка отменила бы первый turn новой группы. Завершение turn'а с ошибкой и неотмеченная задача по-прежнему останавливают прогон — но через чтение `tasks.md`, а не через сигнал запроса (D4).

Следствие: команда может пережить свой запрос. Если к моменту окончания прогона запрос уже прерван, возвращать результат некому, поэтому доклад добавляется в сессию как `runtime-context`-уведомление (`surfaceOp: 'append'`): пользователь читает его в том же транскрипте, а модель не получает turn, которого никто не просил. Живой запрос, как и раньше, получает доклад результатом команды — иначе одни и те же предложения печатались бы дважды.

## Risks / Trade-offs

- **Модель игнорирует «пауза» и делает несколько задач** → стоп-условие проверяет конкретную задачу, поэтому лишняя работа поглощается на следующей итерации, но контекст тратится впустую. Смягчение: D3-секция как опция; диагностика в докладе («отмечено больше задач, чем ожидалось»).
- **Пользователь пишет в сессию во время прогона** → `whenIdle` ждёт его turn; если он задал вопрос, задача останется неотмеченной и прогон остановится. Смягчение: доклад явно называет причину остановки.
- **Сессия без workspace** → новая сессия создаётся по `cwd` и может не появиться в сайдбаре. Смягчение: приоритет `workspaceId`; сценарий описан в README.
- **`openspec` отсутствует или не тот cwd** → ошибка CLI возвращается как результат команды, прогон не стартует. Смягчение: проверка `resolveExecutable` до начала работы.
- **Сжатие внутри задачи вытесняет инструкцию** → включать `protocol.systemSection` вместе с `midTask`; правило зафиксировано в README и в конфиге.
- **Смена сессии на границе группы** → браузер остаётся на исходной сессии; API навигации у плагина нет. Это принятый UX-шов, а не дефект: исходная сессия получает доклад с идентификатором новой.

## Migration Plan

1. Добавить в репозиторий `package.json`, `lib/`, `cordis.patch.yml`, README.
2. В профиле: `pnpm add link:<repo>` и `insert:`-запись в `cordis.patch.yml`.
3. Перезагрузить профиль; команда появляется в списке `/`.
4. Откат: удалить patch-запись и зависимость. Миграции данных нет, формат сессий не меняется.

## Open Questions

- Может ли Web UI автоматически переключаться на только что созданную сессию. API для этого не найдено; на работу прогона не влияет, решается отдельно.
