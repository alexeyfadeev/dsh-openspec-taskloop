# Proposal

## Why

Прогон `/taskloop` останавливается, если после хода агента отправленная задача
перестала опознаваться по тройке `sourcePath` + `line` + дословный `description`.
Достаточно, чтобы модель дописала примечание в строку задачи, исправила в ней
опечатку или вставила строку выше, — и прогон объявляет задачу «исчезнувшей»
(`LOOP_END.missing`), хотя задача та же и работа по ней уже сделана. Именно это
произошло в сессии `session-0b8f1713` на задаче 11.4 (разбор:
`docs/taskloop-missing-stop-2026-11-03.md`). Поведение защитное, но слишком
грубое: оно не отличает «строку переформулировали» от «строку удалили», и любая
правка текста стоит пользователю ручного перезапуска.

Одновременно в спецификации нет ни одного сценария про исчезнувшую задачу: случай
существует только в коде и в комментарии `findListedTask`. Наблюдаемое поведение
не описано, а значит его нельзя ни проверить, ни изменить по правилам.

## What Changes

- **Идентичность задачи по номеру.** Если дословного совпадения нет, задача
  ищется по номеру `N.M` (та же `sourcePath`, иначе ближайшая `line`). Сдвиг
  строки при неизменном тексте перестаёт быть стоп-условием.
- **Оценка расхождения формулировки.** Найденная по номеру задача с другим
  текстом классифицируется детерминированно — `minor` / `gray` / `major` — по
  сохранности старого текста и по сходству строк, а не по «целиком совпало или
  нет».
- **`minor` — прогон продолжается.** Отмеченная задача считается выполненной,
  неотмеченная переотправляется с новой формулировкой. Кейс 11.4 попадает сюда и
  больше не останавливает прогон.
- **`gray` — решает модель, и только когда есть работа.** Один дополнительный
  turn: «та же задача — выполни и отметь, другая — не трогай». Вердикт модели
  читается из галочки, поэтому нового канала ответа не требуется. Если задача уже
  отмечена, спрашивать модель нечего — вопрос уходит пользователю.
- **`major` — решает пользователь.** Отмеченная задача со значительно изменённым
  текстом останавливает прогон с причиной в сессии; неотмеченная — задаёт вопрос
  «формулировка задачи `N.M` изменилась. Было: … Стало: … Продолжить выполнение
  этой задачи?» с вариантами `Продолжить` и `Остановить taskloop`.
- **Причина остановки всегда называется.** `missing` заменяется набором исходов с
  различимой причиной: задачи с таким номером больше нет, задача отмечена при
  значительно изменённой формулировке, пользователь выбрал остановку, спросить
  было некого.
- **BREAKING** (поведенческое, не API): прогон, который раньше останавливался на
  переписанной задаче, теперь продолжается. Пользователь, полагавшийся на стоп как
  на защиту от правок `tasks.md`, увидит продолжение работы.

## Capabilities

### New Capabilities

Нет: поведение целиком принадлежит существующей возможности.

### Modified Capabilities

- `openspec-taskloop`: добавляется требование «Расхождение формулировки
  отправленной задачи» (поиск по номеру, классификация расхождения, продолжение
  или вопрос пользователю, причина остановки) и уточняется требование
  «Завершение задачи определяется по tasks.md» в части исчезнувшей задачи.

## Impact

- `lib/tasks.js` — поиск задачи по номеру рядом с `findListedTask`.
- `lib/diverged.js` (новый) — классификация расхождения, текст адъюдикации, один
  turn адъюдикации.
- `lib/loop.js` — ветка `LOOP_END.missing` заменяется лестницей решений; новый
  шов подтверждения и новые исходы прогона.
- `lib/control.js` — карточка вопроса и причин в докладе.
- `lib/environment.js` — вопрос пользователю через `ctx.get('userQuestions')`.
- `openspec/specs/openspec-taskloop/spec.md` — новое требование и сценарии.
- Тесты: `test/diverged.test.mjs` (новый), `test/tasks.test.mjs`,
  `test/loop.test.mjs`, `test/control.test.mjs`.
- Конфигурация не меняется: пороги расхождения — константы кода, не настройки.
- Зависимости не добавляются: сравнение строк считается на месте.
