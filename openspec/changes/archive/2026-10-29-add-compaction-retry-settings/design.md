# Design

## Context

См. `proposal.md` — Why. Здесь только то, на что опирается реализация.

- `lib/compaction.js` уже содержит всю механику ретраев: `compactBetweenTasks` считает бюджет один раз на входе (`budget = max(1, trunc(attempts))`), спит через инъектированный `sleep` (по умолчанию `waitFor`, который разрешается по abort), и различает коды через `codeOf(error)` и `isRetryable(code, codes)`. Менять нужно не форму цикла, а источник чисел и правило потолка.
- Потолок реализован как `delayBefore = min(delayMs * factor ** (attempt - 1), maxDelayMs)` — то есть при базе 40 секунд и потолке по умолчанию 10 000 мс каждая пауза превращается в 10 секунд. Потолок и база сейчас не связаны, и связать их нечем: оба читаются из одного объекта.
- `compaction.retry.*` — обычные (не volatile) поля `Config`. Плагин строит компактор один раз в `createControl` (`lib/control.js`), захватывая `config.compaction.retry` по ссылке, поэтому правка профиля не доезжает до прогона без перезапуска.
- Settings показывает и принимает к записи только volatile-поля: `volatileForm(schema)` собирает форму из листьев с `meta.volatile`, а `isVolatilePath` отклоняет запись в путь, у которого нет volatile-предка. Значит «переехало в Settings» и «стало volatile» — это одно и то же действие.
- Клиентская половина (`lib/client.js`) пишет каждое изменение сразу через `form.mutate([{ op: 'set', path, value }])`, без кнопки Save; отказ хоста показывается строкой `COPY.failed`/`COPY.refused`.
- Числовые поля в Settings возможны двумя способами: поштучный `Input` с черновиком и записью по blur/Enter, либо `SettingsFormModel` + `settingsNumberField` + `SettingsValueField`, как у лимитов субагентов и таймаута shell — но тот путь требует карточки с кнопкой Save.
- Дефолты конфигурации сверяются тестом `test/config.test.mjs` с блоком `<!-- config-defaults -->` из design.md; блоки всех changes объединяются поверх базового контракта, поэтому этот change описывает только изменяемые ключи.
- Ошибка сжатия несёт только `code` и `message` (`ManualCompactionError`); ни HTTP-статуса, ни `Retry-After` в ней нет, и 429 провайдера приходит кодом `summary` — неотличимо от любого другого сбоя суммаризации.

## Goals / Non-Goals

**Goals:**

- Пауза между попытками сжатия задаётся на странице плагина тремя числами и применяется без перезапуска Harness.
- Дефолтная пауза достаточна, чтобы пережить окно TPM-квоты провайдера, а не только мгновенный сбой.
- Потолок перестаёт молча обнулять настроенную задержку.

**Non-Goals:**

- Различать 429 от прочих сбоев суммаризации: данных для этого в ошибке нет.
- Отдельная пауза для отдельных кодов (`busy` против `summary`): набор чисел один на все повторяемые коды.
- Изменение замороженной тройки `changed` / `commit` / `cancelled`.
- Пересмотр политики `onFailure` и её переезда в Settings — он там уже есть.
- Новый контрол для `codes` и для `maxDelayMs` на странице: оба остаются профильными.
- Пауза перед первым вызовом сжатия или между задачами разных групп.

## Decisions

### D1. Volatile — три листа `retry`, а не весь `retry`

`compaction.retry.attempts`, `delayMs` и `factor` получают `.volatile()`. `retry.codes` и `retry.maxDelayMs` остаются обычными полями.

Причина: `.volatile()` на самом узле `retry` тоже работает (`volatileForm` возвращает `plainSchema` для volatile-узла, `isVolatilePath` разрешает любой путь под ним), но тогда в форму namespace попадают все пять полей, включая `codes` — массив строк, редактируемый через API настроек. Список транзиентных кодов — свойство интеграции с сервисом сжатия, а не пользовательская настройка, и дать ему случайно оказаться в форме хуже, чем добавить три `.volatile()`.

Следствие: разрешённый `Config` содержит три `Volatile`-обёртки внутри `compaction.retry`, и любой код, читающий эти числа, обязан вызывать `.get()`. `resolveConfig` не меняется: он по-прежнему возвращает уже разрешённый конфиг как есть.

Альтернативы:
- *Весь `retry` volatile.* Меньше строк, но `codes` становится записываемым из UI namespace.
- *Оставить всё профильным и только поменять числа.* Ноль клиентского кода, но не решает вторую половину задачи: у других провайдеров другие окна.

### D2. `maxDelayMs: 0` — «потолка нет», а положительный потолок не опускается ниже базы

Правило вычисления паузы становится таким:

```
ceiling    = maxDelayMs > 0 ? max(maxDelayMs, delayMs) : Infinity
delay(n)   = min(delayMs * factor ** (n - 1), ceiling)
```

Два следствия, оба нужны:
- `0` (новый дефолт) означает отсутствие потолка: рост ограничен числом попыток, а не отдельной константой. Именно это позволяет базе 40 секунд дать 40 → 60 → 90.
- Положительный потолок сохраняет смысл «не ждать дольше N на одну паузу», но не может быть ниже базовой задержки: иначе настройка «первая пауза 40с» при профильном потолке 10с молча превращалась бы в «10с», что и есть сегодняшняя ловушка.

Альтернативы:
- *Убрать `maxDelayMs` из схемы.* Чище, но ломает профили, где он задан, и отнимает единственный тормоз для тех, кто поставит `attempts: 10` и множитель 5.
- *Оставить дефолт 10 000 и не трогать правило.* Тогда 40 секунд недостижимы в принципе.

### D3. Дефолты — наблюдаемые числа провайдера, а не осторожные

`attempts: 4`, `delayMs: 40000`, `factor: 1.5`, `maxDelayMs: 0`.

Обоснование: дефолт в одну секунду доказуемо бесполезен против окна TPM, а настройка, которую никто не открывал, не работает. Цена дефолта платится только на пути отказа — успешное сжатие не ждёт ни одной паузы, потому что пауза стоит между вызовами, а не перед первым.

Альтернатива: оставить 1с / ×2 / 3 и попросить пользователя ввести свои значения один раз. Отклонено: тогда из коробки плагин по-прежнему умирает на первой же минуте квоты, а пользователь узнаёт об этом из остановленного прогона.

### D4. Числовые поля пишутся по blur/Enter, без карточки с Save

Три числа живут на той же странице, что и тумблеры, пишутся тем же `form.mutate` — по blur или Enter, с локальным черновиком на время набора. Отказ хоста (значение вне `min`) показывается существующей строкой ошибки, а поле возвращается к сохранённому значению из снапшота.

Под полями — вычисленная строка: «40с → 60с → 90с, худший случай 3m10s». Она считается из текущих значений тем же правилом, что и D2, включая отсутствие потолка, и снимает главный вопрос к таким полям: во что обойдётся набор.

Альтернатива: `SettingsFormModel` + `SettingsValueField` + карточка с кнопкой Save, как у лимитов субагентов. Даёт готовую валидацию и кнопку сброса, но на одной странице оказалось бы два способа сохранять: тумблеры применялись бы сразу, а числа — по кнопке. Разные правила для соседних строк хуже, чем десяток строк собственного состояния.

### D5. Числа читаются на каждом переходе, а не на старте прогона

`compact` в `lib/control.js` остаётся одним на плагин, но собирает объект `retry` перед каждым вызовом `compactBetweenTasks`, вызывая `.get()` у трёх ссылок (и беря `codes` и `maxDelayMs` как обычные значения).

Почему не снимок на старте прогона, как у `onFailure`: снимок потребовал бы протащить объект `retry` через `startRun` → цикл → переход, то есть изменить сигнатуры ради поведения, которое пользователь не увидит, — «применится следующим прогоном» выполняется и так. Чтение на переходе дополнительно позволяет уменьшить паузу, увидев, что прогон встал на 40 секундах, не перезапуская его.

Внутри одного перехода бюджет фиксируется на входе в `compactBetweenTasks`, поэтому переключение настроек посреди серии попыток не может растянуть её сверх того, что было посчитано.

### D6. Изменённые дефолты документируются отдельным блоком

Изменённые числа попадают в блок `<!-- config-defaults -->` этого design.md, а не в базовый контракт: `test/config.test.mjs` объединяет блоки всех changes поверх дефолтов базового и сравнивает с `Config({})`, поэтому change описывает только свои ключи, а `codes` и остальная конфигурация остаются описаны там, где были.

Профили, в которых `compaction.retry` задан явно, сохраняют свои значения; меняются только те, что полагались на дефолты.

<!-- config-defaults -->
```json
{
  "compaction": {
    "retry": {
      "attempts": 4,
      "delayMs": 40000,
      "factor": 1.5,
      "maxDelayMs": 0
    }
  }
}
```

## Risks / Trade-offs

- **Прогон молчит до трёх минут.** → Пауза прерывается `/taskloop stop` (существующий `waitFor`), худший случай виден на странице до прогона, а политика `continue` позволяет не ждать вовсе.
- **Один набор чисел обслуживает и `busy`, и 429.** `busy` разрешается за секунды, но будет ждать 40. → Приемлемо: `busy` означает, что прогон уже остановлен, а различить коды нельзя — в ошибке нет ничего, кроме `code` и `message`.
- **`maxDelayMs: 0` убирает тормоз для экстремальных настроек.** `attempts: 10` с множителем 5 и базой 40с — это часы. → Потолок остаётся доступен в профиле, а страница показывает худшее суммарное ожидание при любом наборе.
- **Три volatile-листа меняют форму разрешённого конфига.** Код и тесты, читавшие `config.compaction.retry.attempts` как число, получат ссылку. → Правка локализована: `lib/control.js` и тесты, конструирующие конфиг для компактора; `compactBetweenTasks` продолжает принимать обычные числа.
- **Смена дефолтов меняет поведение профилей, которые ничего не задавали.** → Это цель change; откат — вернуть числа в профиле, миграция не нужна.
